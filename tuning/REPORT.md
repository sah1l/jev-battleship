# Prompt tuning: option descriptions, 2026-09-20

Model jev-1.13.0. Goal: better play with no local strategy. Local code still only keeps the shot legal.

## What the probe showed

Baseline (previous production prompt), 8 seeded fleets: 47.6 shots, density benchmark 29.0, random 57.3.

- Target play was already fine: 93% of shots next to a hit, lines followed 31/35.
- Hunt play was the whole problem. Jev fired A1 A2 A3 A4 ... B1 B2 B3, extending runs of misses
  in reading order. Its hunt picks ranked about 30th of the open cells by density, no better than random.

## What was tried

Position diagnostic: 19 hunt, 12 target, 16 single-ship tactical boards (`positions.mjs`).
Hunt quality is the chosen cell's density relative to the best cell (offline grading only).

| Variant | What changed | Hunt quality | Tactical | Mean shots, 8 dev fleets |
|---|---|---:|---:|---:|
| previous | | 0.45 | 12/16 | 47.6 |
| valid-only | fired cells not offered | 0.51 | 12/16 | |
| two-case / open-water | literal two-case instructions | 0.71 / 0.58 | 13 / 14 | |
| reason | explains why open water matters | 0.81 | 12/16 | 40.1 |
| hit-first | reason + hits take priority | 0.70 | 14/16 | 48.1 |
| hit-first, grid only / lists | smaller state | 0.56 / 0.53 | 10 / 15 | |
| neighbours | each option lists its 4 neighbours' states | 0.96 | 11/16 | 29.8 |
| look2 / look2-literal | 2 cells per direction, one list | 0.82 / 0.89 | 16/16 | 32.0 / 33.6 |
| look2-near | same, hunt keyed to nearest cell | 0.90 | 16/16 | 32.8 |
| **near-far (kept)** | neighbours sentence + "one further" sentence | 0.91 | 16/16 | 26.3 |

Instruction wording alone barely moves real games. Jev cannot read spatial structure off the grid,
but it reads option descriptions literally. Stating each option's observed surroundings is what works.
`neighbours` hunts in a natural checkerboard but cannot tell an in-line extension from a sideways
neighbour (lines followed 82/118). The "one further" sentence fixes that (80/83) without hurting the hunt.

near-far and neighbours are tied on shots within noise; near-far was kept for its line-following,
which is what a human opponent notices. Tokens per match fell from about 140k to about 105k.

Known remaining leak: finding the last 2-cell ship late in the game, when every open cell has a fired
neighbour. Two endgame wordings, `near-far-end` and `near-far-end2` in `variants.mjs`, were graded on
39 late positions sampled from saved games and made no difference (0.83 to 0.86), so wording has
plateaued there. That probe read the raw game files, which are not committed, so it is not here either.

## Is this still "no code logic"?

The descriptions are lookups of observed cell states around each option. Nothing is counted, scored,
ranked or filtered, and the same sentence template is used for every option on every turn.
The only filtering is legality: fired cells are not offered.

## Reproduce

~~~powershell
node probe.mjs 8 --seed 20261301                       # current production prompt
$env:VARIANT='previous'; node probe.mjs 8 --seed 20261301 --request-module ./tuning/variant-shot.mjs
node tuning/positions.mjs previous,neighbours,near-far
node tuning/analyze.mjs tuning/near-far-games.json --examples 5
~~~

Every variant is in `variants.mjs`, and `fixtures.mjs` holds the tactical positions with an
objective answer key, graded offline only. Each run writes a `*-games.json` with every board and
probability vector; those files are regenerated by the commands above rather than committed, since
each one is several hundred kilobytes of live-call data.
